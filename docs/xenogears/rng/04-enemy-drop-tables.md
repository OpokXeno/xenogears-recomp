# Enemy Drop Tables

## 1. Scope

This chapter is a data table, not a mechanism description: it presents every
enemy definition slot's drop chances and awarded items across all 76 enemy
sets on Disc 1. The roll formula that consumes this data is already
documented in
[`battle/08` §10](../battle/08-results-progression-and-persistence.md#enemy-drop-rolls)
and is only summarized here, and it is indexed alongside the rest of Battle's
RNG surface in
[`02-battle-rng.md` §8](02-battle-rng.md#8-enemy-drop-rolls-in-detail).

## 2. Roll Formula

Quoted from `battle/08` §10 (`BattleResultRollEnemyDrops`, `0x801E42C4`):

```text
if random_mod_100 < primary_chance or trader_card_equipped:
    award primary
else if fresh_random_mod_100 < secondary_chance:
    award secondary
else:
    emit an empty drop entry
```

The secondary roll only happens if the primary roll fails, so an enemy's two
listed chances are not additive — reading a `20%` primary and `50%` secondary
does not mean a `70%` chance of *some* drop; it means `20%` for the primary
item and, only on that miss, a further `50%` chance (`40%` of the remaining
`80%`, i.e. an actual `20% + 40% = 60%` chance of walking away with something)
for the secondary item. Equipping the Trader Card guarantees the primary
result for every defeated enemy that has one.

A `0%` primary chance with a real item still assigned to that slot is a
deliberate pattern, not a dead slot: since the primary branch is
`random_mod_100 < primary_chance or trader_card_equipped`, a `0%` chance can
never be satisfied by the roll, so that item becomes reachable **only** by
equipping Trader Card. A few enemies use this to gate a rare item behind
Trader Card while still offering an ordinary secondary drop the rest of the
time — for example Shakhan Guard and Dorothy both give a guaranteed
Evasion Ring with Trader Card equipped, or (without it) a `10%` chance at
Gold Bullion instead; equipping Trader Card against either trades away that
Gold Bullion chance entirely, since the two branches are mutually exclusive
per kill. The far more common case (186 of the 326 catalogued slots)
is simpler: `0%` primary chance paired with primary item ID `0` (the empty
sentinel) just means that enemy's only real drop lives in the secondary
slot and the primary slot was never used at all.

## 3. Extraction Method

Each enemy set's own definition file (directory `0x0D`, file
`2 + enemy_set * 2`, per
[`battle/02` §7](../battle/02-loading-resources-and-formations.md#7-enemy-pair))
stores its eight definition slots at `+0x32`, stride `0x170`, per the same
section.
[`battle/08` §10](../battle/08-results-progression-and-persistence.md#enemy-drop-rolls)
already documents that the live `0x170`-byte battle entity is a straight copy
of this static record, so the same live-offset byte layout applies directly
to the file:

| Offset (from definition-slot start) | Field |
|---:|---|
| `+0x150` | Primary chance (compared against `random_mod_100`) |
| `+0x151` | Secondary chance (compared against a fresh `random_mod_100`) |
| `+0x152` | Primary item ID |
| `+0x153` | Secondary item ID |
| `+0x154` | Primary item's inventory class |
| `+0x155` | Secondary item's inventory class |

`tools/extract_enemy_drops.py` reads all 76 enemy sets (definition files
`2..153` in directory `0x0D`) directly off the disc, resolves each occupied
slot's own name through the same `DialogStringBundle` mechanism documented in
[`rng/03-worldmap-encounter-tables.md` §6](03-worldmap-encounter-tables.md#6-enemy-name-resolution),
and reads the six drop bytes above for every slot, plus each slot's maximum
HP (live offset `+0x4E`) for the reason given in Section 4. A slot with no
name and a `0%`/`0%` chance pair is omitted as almost certainly unoccupied;
every enemy set actually referenced anywhere in the game is expected to be
complete below. Enemy set `0` decodes to non-text garbage across every slot
and is omitted entirely — it does not look like a real, occupied enemy set.

## 4. Name Resolution Accuracy

The enemy-set file has no field that declares how many of its 8 definition
slots are real monsters versus never-used padding — the name-bundle index
just keeps going past the real roster into that set's own attack names and
battle messages (Section 8 of
[`02-battle-rng.md`](02-battle-rng.md#8-enemy-drop-rolls-in-detail) already
notes this same string bundle holds both). Positional name resolution is
therefore occasionally wrong once a set's real roster is smaller than 8, and
this was caught during review, not assumed away:

- **Confirmed defect, fixed:** slots whose decoded string is the literal
  autogenerated placeholder `"Monster " + <index>` (e.g. enemy sets 2 and 5)
  are never real display names — `tools/xenogears_text.py`'s
  `is_placeholder_name` detects and suppresses them, falling back to `def<N>`
  like a genuinely unnamed slot.
- **Confirmed defect, not automatically fixable:** Enemy Set 6, slots `5`-`7`
  decode to `"Wake up kiss"`, which is actually one of Shellbelle's attack
  names, not a monster name — those three slots have `0` max HP and `0%`/`0%`
  drop chances, consistent with being unused padding that happens to land on
  real attack text instead of raw garbage bytes. This was found by manual
  review, not detected automatically, and other enemy sets not covered by
  World Map data (below) could have the same kind of misattribution
  undetected.
- **`def<N>` is not always "no data"**: several slots decode to raw non-text
  bytes for their name but have real, nonzero stats and drops (e.g. Enemy Set
  47 — the "Big Joe's fans" wrestling minigame — has real HP and drop chances
  on slots with no authored name at all). Max HP is included in the table
  specifically so a `def<N>` row can be read correctly: nonzero HP or a
  nonzero chance means a real, playable combatant that the original game
  simply never named on-screen; all-zero stats alongside `def<N>` more likely
  means genuinely unused padding.
- **`[World Map-confirmed]`** marks a slot independently verified against the
  actual formation data in
  [`03-worldmap-encounter-tables.md`](03-worldmap-encounter-tables.md) — some
  known formation really does place that exact `(enemy set, slot)` combination
  in a fight. Its *absence* is not evidence a name is wrong: most named
  enemies (bosses, scripted events, minigames) never appear as a World Map
  random encounter at all, so the majority of correct names in this table
  carry no marker. An earlier version of this tool flagged every unconfirmed,
  all-zero-stat slot as suspect, which produced far more false alarms (Deus,
  a definite final-boss name, has `0` HP and `0%`/`0%` chances and is not a
  World Map encounter) than genuine catches, so that automatic flag was
  removed in favor of the two confirmed cases above plus this explanation.

## 5. Item Identification

Each drop's item ID is resolved to a real name through the shared item-name
database, documented in full in
[`menu/03` §12](../menu/03-resource-and-string-formats.md#12-item-weapon-and-accessory-name-database).
An item ID is local to its own inventory class, not a global identifier —
`Gear weapon #1` and `Consumable/key item #1` are unrelated items that
happen to share a number, so every entry below is labeled with both:

| Class | Inventory |
|---:|---|
| 0 | Character weapon |
| 1 | Character accessory |
| 2 | Consumable/key item |
| 3 | Gear part |
| 4 | Gear weapon |

A drop shown as a bare `#<N>` (rather than a name) means that ID's database
entry decoded to raw, non-text bytes — a handful of IDs across the whole
table (13-15, 27, 29, 30, 47, 49, 85 in the Gear weapon class) are like this
and appear to be genuinely unused/placeholder slots in the source data
itself, not an extraction gap.
